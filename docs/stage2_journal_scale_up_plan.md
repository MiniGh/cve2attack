# Stage 2 论文级扩大验证方案

本文记录以论文投稿为目标的 Stage 2 扩大验证方案与路线。本项目只有 Stage 1 与 Stage 2 两个
阶段；本文不是第三阶段，而是 Stage 2 现有方法的扩大验证规划。

生成时间：2026-08-08。方法内核不变，仍为 `topology-rule-priority-v2`（未修改）。

## 0. 一句话定位

方法不变，把验证从"简单图上的小样本案例研究"扩大为"可信标签下的受控实验"。毕设闭环已完成，
结论见 `docs/stage2_closing_report.md`；本文只规划其后的扩大验证。

## 1. 为什么要扩大：当前证据的真实状态

按"标签是否与图描述同一攻击步骤"盘点已完成实验：

- **有效性正面证据只有 1 例**：Zerologon（CVE-2020-1472，T1210 从第 13 升到第 1）。其标签来自
  M&NTIS 轨迹对该攻击步骤本身的标注，与图同源、位置敏感，是理想形态。
- 无伤害证据 5 例（扩展 LPE 四例 + PwnKit）：只能说明 v2 不破坏 Stage 1 已正确的排名，不能证明
  有效性；且其标签来自 CTID KEV（CVE 级词典，位置无关），本就无法支撑有效性主张。
- 失败归因 1 例（Tatsu，Stage 1 未召回）、设计驱动 1 例（Sudo，用于设计 v2）。

结论：方法有效性的独立正面样本 n=1。这是投稿的核心缺口，不是"样本量 8 偏少"，而是"能证明
有效性的样本只有 1 个"。

## 2. 地基前提：标签必须轨迹原生且位置敏感

这是整条路线的地基，必须最先满足，否则后续实验无法评价。

每个测试用例需要两样相互独立的东西：

1. **攻击图**：CVE 摆在什么拓扑位置。来源可为场景转换器（`scenario_graph.py`，从轨迹生成）或
   MulVAL（从网络配置生成）。
2. **标准答案**：该位置上正确的 ATT&CK technique。

标准答案的三个可能来源及其适用性：

| 来源 | 位置敏感 | 与图同源 | 能否支撑受控实验 |
| --- | --- | --- | --- |
| CTID KEV CVE 级词典 | 否 | 否 | 不能：换位置答案不变 |
| 轨迹原生逐步标注（M&NTIS 式） | 是 | 是 | 能 |
| 人工标注 | 是 | 否 | 弱：主观、有泄漏风险 |

因此扩大实验必须使用**轨迹原生逐步标注**的数据源；CTID KEV 只能用于 CVE 级的辅助核对，不能作为
受控实验的主标签。

## 3. 核心矛盾：图规模与标签可信之间的张力

两个目标互相拉扯，是本路线真正要解决的设计难题：

- 想要**大而真实、一图多 CVE** 的攻击图 → 倾向 MulVAL 合成 → 但合成图没有配套的位置敏感标签，
  只能人工标，与防泄漏纪律冲突；
- 想要**位置敏感、可信的标签** → 倾向轨迹数据 → 但轨迹派生图通常很小（如毕设中的 4 节点图），
  正是审稿会质疑的"图太小"。

期刊既嫌图小、又要标签可信，而两者来自相反方向。方案设计必须显式回答如何取舍或折中，
不能默认"用 MulVAL 生成大图"就能解决，因为那条路缺标签。

可能的折中方向（待定，需先有数据再判断）：

- 深挖轨迹数据集，寻找本身较大或可串联为多跳的真实轨迹；
- 轨迹提供标签与骨架，半自动扩充周边拓扑以增大图规模，同时严格保持标签只来自轨迹；
- 多个真实轨迹合成到同一网络配置中，形成一图多 CVE，但每个 CVE 的标签仍取自其原轨迹。

## 4. 受控实验设计（方法有效性的主证据）

> **更新（2026-08-09，见文末 E1 执行记录）**：E1 测量表明"外部 T1190 / 内部 T1210"这条网络位置轴在真实数据里几乎不存在（T1210 仅 3 个 CVE、lateral-movement 仅 7 个），本节据此作废，改为按"角色/阶段"轴（exploitation vs impact）设计，详见 E2 方案。

核心思想：**同一个 CVE 放在不同攻击位置，CVE 文本不变 → Stage 1 候选不变 → 唯一变量是图中的
位置**，观察 Stage 2 重排是否随位置正确变化。这是因果性证据，强于案例堆砌。

- 位置族聚焦**外部入口**与**横向移动**——这两族拓扑有区分力，Zerologon 已证明有效；
- **本地提权族不再投入**：毕设已证明其"0 提升"是 topology-only 证据的原理边界，继续投入仍为
  0 提升；
- 位置变化的实现有两种，需先定：(a) 用数据集中天然处于不同位置的真实案例；(b) 人为把同一 CVE
  放到不同拓扑位置。(a) 更真实但受数据限制，(b) 更干净但需论证合理性。

## 5. 对照基线（回应"为什么不直接用 LLM/学习方法"）

1. Stage 1 原始排名（已有）；
2. **LLM 重排**：把图上下文与候选交给大模型重排；
3. **学习式排序**：以图特征训练（如 LambdaMART / 逻辑回归），严格划分训练/测试；
4. 随机基线 + oracle 上界（界定可提升空间）。

## 6. 指标与统计

- 指标：Top-1、Top-3、MRR、nDCG，并**按位置族分开报告**（有效性活在族的区分里）；
- 统计：样本上百后做显著性检验。Stage 1 已有
  `src/cve2attack/evaluation/paired.py`（逐例配对 bootstrap，固定 seed，95% 置信区间），可直接复用；
- 报告须同时给出提升、保持、退化、不可恢复四类计数，不只报平均值。

## 7. 开工前必须先解决的前置条件（来自 §28 评估）

三项均须在**查看任何新标签排名之前**完成，否则重回"照答案调规则"：

1. 固化上游图生成仓库状态，明确正式实验使用的代码版本与 MulVAL 交互规则集；
2. 就"真实图上多条规则同时命中如何裁决"形成独立预注册（毕设图每例只命中一条，从未评估）；
3. 明确 `networkServiceInfo` 等事实应从证据子图还是全图事实读取，先预注册再改规则。

图生成侧的工具链评估见 `docs/stage2_upstream_graph_generator_assessment.md`；该文只覆盖图生成，
不涉及标签策略。

# 执行记录

按 E1 → E2 → E3 顺序记录每环的方案与实测。方案执行前确定，结果执行后回填；不符合预期即停下记录原因。
本记录于 2026-08-09 整理过一次：去除了探索过程中的重复与被取代的粗糙设计，只保留当前有效的方案与
结论；被取代的思路以简短"演进说明"保留供追溯，不占正文。所有数字均可由所列脚本复现。

## E1 现象层：CVE→technique 映射是否依赖上下文

**方案**：用已冻结的 CTID KEV→ATT&CK 映射（`data/raw/kev/kev-02.13.2025_attack-15.1-enterprise.csv`，
sha256 `8f15aab4…`，ATT&CK Enterprise 15.1）+ ATT&CK 15.1 语料，统计同一 CVE 是否对应多个 / 跨 tactic
的 technique。子技术上卷父技术，纯只读。预注册 go/no-go：多用途 ≥~25% → 进 E2。

**结果（296 CVE）**：带 ≥2 个父 technique 的 **82.1%**；exploitation_technique ≠ primary_impact 的
**76.4%**；technique 跨 ≥2 个 tactic 的 **80.1%**。（附注：KEV 中 lateral-movement 仅覆盖 7 个 CVE、
含 T1210 仅 3 个——这决定了 E2 不能用"总体统计"证 T1190/T1210，只能用构造演示，见下。）

**结论（强通过，进 E2）**：映射的上下文依赖是普遍现象——上下文盲的单值映射约 80% 情况下在多个合法
答案中被迫只选一个。复现：`/tmp/e1_measure.py`。

## E2 方法层：图上下文能否选出位置适配的 technique

**论点**：同一 CVE 的多个合法 technique 中该用哪个，取决于它在攻击图中的位置；纯文本方法只能给出与
位置无关的单一答案，因此对位置不同的用法必错其一；图上下文能补上位置信号并纠正。

**演进说明（供追溯，不是当前方案）**：最初设想以"外网 T1190 / 内网 T1210"做总体统计，E1 发现 KEV 中
横向样本过少（T1210 仅 3 例），总体统计轴作废；改为"构造同一 CVE 两种真实上下文"的受控演示 + 规模化。
中途另试过一版以 initial-access 粗规则、按 CTID 利用/影响面评分的统计，它能解析入口/利用方向、却无法
解析弥散的影响侧——该粗规则已被下面更干净的设计取代，其"影响侧不可解析"作为方法边界保留在末节。

**前提检查（先于任何代码，纯数据）**：利用类与影响类 technique 能否用内在 tactic 区分？（否则规则读
不到、必须碰标签＝泄漏。）结果：exploitation 类 **74%** 属 initial-access，primary_impact 类仅 **4%**；
逐 CVE 两类 tactic 集合 **95%** 可区分。→ 可用图无关信号区分，无泄漏。

**主证据 A · 构造演示（机制铁证，5 个知名服务型 RCE）**：同一 CVE 构造外网入口图与内网横向图
（`scenario_graph.py` 渲染），跑**现有未改动的 v2 规则**。ProxyLogon 内网 T1210 由第 12→第 1、
Spring4Shell 3→1、BlueKeep 外网 T1190 8→1、PaperCut 双向→1、Exchange(2020-0688) 内网 4→1。
5 例、两方向共 10 个 (CVE,上下文) 全部命中 Top-1；盲排序两上下文给同一固定排名，必错其一。
复现：`/tmp/e2b_demo.py`。

**主证据 B · 规模化（n=91，Stage1 Top-20 同时召回 T1190/T1210 的 CVE）**：同法构造两上下文，配对
bootstrap seed=20260809 B=10000。规则触发 91/91。

| 上下文 | 真值 | 盲 Top-1 | 重排 Top-1 | 盲 MRR | MRR 提升(95%CI) |
| --- | --- | ---: | ---: | ---: | --- |
| 外网 | T1190 | 34% | 100% | 0.479 | +0.521 [0.439,0.601] |
| 内网 | T1210 | 2% | 100% | 0.178 | +0.822 [0.783,0.854] |

两上下文都命中 Top-1：**盲排序 0/91**（单一固定排名结构上不可能），**看图重排 91/91**。
复现：`/tmp/e2b_scale.py`。

**诚实标注（防过度解读）**：重排 Top-1 100% 是**规则构造的必然**——`public_facing_service` 只促 T1190、
`lateral_remote_service` 只促 T1210，触发即置顶。信息量全在**盲基线**与**触发可靠性**，不在重排数字。
入选口径为"Stage1 同时召回 T1190/T1210"（双上下文皆合理的代理），未人工过滤以避免 cherry-pick；
构造图真实合理（Exchange/RDP/Web 服务本就既可外网暴露又可内网横向），属构造演示的规模化，非野外样本。

**E2 结论**：核心论点成立且经得起审稿——现象普遍（E1 76–80%）、文本方法在位置依赖技术对上系统失效
（内网 T1210 Top-1 仅 2%、两上下文 0/91）、图拓扑可靠提供位置信号（91/91）。方法侧对 T1190/T1210
近乎"定义即正确"（ATT&CK 本按位置定义二者），故论文论点应落在"文本方法系统失效、图拓扑是必需信号"，
而非"本方法准确率高"。

**E2 已知边界（limitation，如实写入论文）**：
1. 拓扑只能干净解析位置清晰的技术对（入口/横向 → T1190/T1210）；对影响侧弥散的 technique
   （execution/privesc/impact 混杂）无法机制级区分——与 Stage 1 阶段既有结论一致，是 topology-only
   证据的固有边界。
2. Stage 2 只能重排 Stage 1 已召回的候选；两目标技术未同时被 Top-20 召回的 CVE 不在适用范围，
   归因于 Stage 1 召回而非 Stage 2。
